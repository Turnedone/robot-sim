# 6. ROS 2

Code: [`ros2/robot_sim_ros`](../ros2/robot_sim_ros) · ROS 2 Jazzy, C++ (`rclcpp`)

The same robot core runs as ROS 2 nodes, unchanged: the core has no graphics and no ROS in it, so
everything ROS-specific lives in a thin layer around it ([`conversions.hpp`](../ros2/robot_sim_ros/include/robot_sim_ros/conversions.hpp)).
The nodes use the **standard message types and topic names**, so ROS tools work with them
(RViz, `ros2 topic`, `ros2 bag`) and each node could be swapped for a standard one.

## Nodes

| Node | Subscribes | Publishes | Stands in for |
|---|---|---|---|
| `sim_node` | `/cmd_vel` | `/scan`, `/odom`, TF `odom → base_link`, `/ground_truth` | the robot and its drivers |
| `localizer_node` | `/scan`, `/odom`, `/initialpose` | `/map` (latched), `/particlecloud`, `/amcl_pose`, TF `map → odom` | AMCL + map_server |
| `mapper_node` | `/scan`, TF | `/map` | a mapper (mapping only, not SLAM) |
| `navigator_node` | `/goal_pose`, `/map`, TF `map → base_link` | `/cmd_vel`, `/plan` | Nav2 |

## The TF tree

```
map ──(localizer_node)──► odom ──(sim_node)──► base_link
```

- `odom → base_link` is odometry: smooth, but drifts as the wheels slip.
- `map → odom` is the localizer's correction: `map→odom = estimate · (odom→base_link)⁻¹`. Publishing
  the correction as a separate transform (instead of `map → base_link` directly) is the ROS
  convention (REP 105): it keeps `odom → base_link` continuous for controllers, while the
  correction may jump.
- In mapping mode a static `map → odom` identity is published instead, and odometry does not slip.

## On Windows: WSL2

Windows 11 runs Ubuntu, including graphical programs like Gazebo and RViz, through WSL2:

```bash
wsl --install -d Ubuntu-24.04          # in an administrator PowerShell, then restart
wsl -d Ubuntu-24.04 -u root -- bash /mnt/c/<path>/robot-sim/tools/wsl/setup-ros2-gazebo.sh
wsl -d Ubuntu-24.04 -- bash /mnt/c/<path>/robot-sim/tools/wsl/check-ros2-gazebo.sh
wsl -d Ubuntu-24.04 -- bash /mnt/c/<path>/robot-sim/tools/wsl/build-ros2.sh --test
```

The setup script installs ROS 2 Jazzy, Gazebo Harmonic (`ros_gz`), Nav2 and Nav2's TurtleBot3
simulation; the build script builds and tests this package straight from the repository.

## Our nodes driving a TurtleBot3 in Gazebo

```bash
ros2 launch robot_sim_ros gazebo.launch.py          # then RViz "2D Goal Pose", or:
bash tools/wsl/goal.sh 2.0 -0.5                       # send a goal from the command line
bash tools/wsl/where-is-robot.sh                      # Gazebo's ground truth vs our estimate
```

This starts Gazebo Harmonic with Nav2's TurtleBot3 world and robot, a standard `map_server` with
that world's saved map, and **our** `localizer_node` and `navigator_node` in place of AMCL and Nav2.
Nothing else is shared with Nav2.

What it took, beyond the nodes themselves:

| | Why |
|---|---|
| **Map origin** | ROS maps can start anywhere (this one at (−10, −10)); the core's maps start at 0. The nodes shift poses by the origin on the way in and out. |
| **Inflation** (`inflation_radius` 0.25 m) | With 5 cm cells the robot is ~9 cells wide; cells closer to a wall than its radius are blocked, and a clearance cost keeps paths in the middle of passages (Nav2's inflation layer). |
| **Path smoothing** (`smooth_path`) | A\* on 5 cm cells gives a staircase of tiny corners; string pulling turns it into a few straight segments, so the corner-limited pure pursuit does not stop every 5 cm. |
| **Lidar offset** (`sensor_x` −0.064 m) | The TurtleBot3's lidar is 6.4 cm behind its centre; beams are cast from there. |
| **Simulated time** (`use_sim_time`) | Gazebo has its own clock; every node and tool must use it or TF lookups fail. |
| **Model path** | Gazebo must be told where the TurtleBot3 world's 3D models are (`GZ_SIM_RESOURCE_PATH`). |

Result on the first run: from (−2.0, −0.5) to (2.0, −0.5) around the pillars in 14 s; Gazebo's
ground truth (1.876, −0.471), our estimate (1.890, −0.517): **under 5 cm localization error** with
the real TurtleBot3 lidar, physics and wheel odometry.

## Running it (Linux with ROS 2 Jazzy)

```bash
mkdir -p ~/ws/src && cd ~/ws/src
git clone https://github.com/Turnedone/robot-sim.git
cd ~/ws
rosdep install --from-paths src --ignore-src -y
colcon build --base-paths src/robot-sim/ros2
source install/setup.bash

ros2 launch robot_sim_ros localization.launch.py                      # saved map, slipping wheels
ros2 launch robot_sim_ros localization.launch.py map:=maze global:=true
ros2 launch robot_sim_ros mapping.launch.py                           # build the map from scratch
```

In RViz, **2D Goal Pose** sends the robot somewhere (`/goal_pose`), **2D Pose Estimate** tells the
localizer where the robot is (`/initialpose`).

## How it is tested

- `test_conversions`: quaternions, 2D transform composition (including the `map → odom`
  formula), laser scans, and occupancy grids — ROS stores grid rows from the **bottom** up while
  the core stores them from the top down.
- `test_nodes`: the simulator, localizer and navigator run in one process but talk only through
  topics and TF; a goal is published like RViz's 2D Goal Pose, and the simulated robot must
  **really** arrive (checked against the ground truth) with the localizer agreeing.

Both run in CI in the official `ros:jazzy` Docker image (`colcon build` + `colcon test`).
Not tested automatically: the launch files and the RViz layout (they need a display).

## Differences from the viewer

- The ROS navigator does not hold the robot still while localization is unhealthy (the viewer and
  the core tests do). The localizer could publish its health so the navigator can do the same.
- `gazebo.launch.py` is run by hand, not in CI (Gazebo needs far more than the CI container has).
- Timing is wall-clock (ROS timers) instead of the viewer's fixed-step loop, as on a real robot.
